BioTime ↔ Odoo: six modules, one blueprint

A close reading of every BioTime integration module on the Odoo apps store — what each one does, what they all share, where they differ, and the feature set worth building into our own connector.

01Executive summary

All six modules solve the same core problem — pull raw punch data from a ZKTeco BioTime server over its REST API and turn it into hr.attendance records — but they differ sharply in engineering maturity. Three are thin cron scripts, two are solid mid-market products, and one (ms_bitotime) is the most technically ambitious despite being the second cheapest.

The market consensus architecture is: server config model → employee mapping by BioTime code → raw transaction staging table → pairing engine → hr.attendance, driven by a configurable cron. The modules that stand out add reliability engineering — idempotent re-pulls, background job queues with retries, per-punch error states — and smart interpretation — late-in detection, missing-checkout flags, night-shift handling, per-employee timezones. Those two axes are exactly where our extension should aim.

02The six modules, one by one

1 · biotime_sync — Hunter BI

€449–649OPL-12,381 LOCv19
"The premium product" — business rules, dashboard, role-based access.
  • Auth flexibility is its party trick: Token, JWT and Basic authentication — the only module advertising multiple auth schemes.
  • Business rules engine: work start/end time, break duration (auto-deducted from worked hours), late tolerance (grace period), overtime threshold, sync interval — all configurable.
  • Smart calculations: worked hours, late detection, overtime computed automatically.
  • Dashboard with real-time attendance statistics, charts and KPIs.
  • Three access roles: User / Supervisor / Manager.
  • Employee matching by BioTime ID or barcode; paginated API fetching; sync logs with status tracking and error details; Test Connection button.
Take-away: the clearest picture of the "complete" commercial feature set — HR-rule configuration and a dashboard. No mention of error-state queues or two-way sync.

2 · yasir_biotime_server_integration_v18 — Eng. Yasir Habeeb

$590LGPL-3612 LOCv18/v19
Small, focused BioTime 8.5 sync — sold at a premium on documentation quality.
  • Server record: IP, Port, Username, Password, Page size, Start time (Start time prevents importing very old transactions — an incremental-pull cursor).
  • Test Connection and Get transactions buttons on the server record.
  • Employee mapping via a Biotime Code field on the employee's Settings tab (INFO BIOTIME section) — must match the BioTime user ID.
  • Cron every 7 minutes (the tightest polling interval of the six), fetching transactions and auto-creating attendance.
  • Handles multiple punch-in/punch-out scenarios, late check-ins, early check-outs, missing punches; multi-device/multi-terminal environments; "safe duplicate-prevention logic".
  • Manual synchronization wizard for on-demand updates; dedicated menus for transactions, employees and logs under Attendances → Biotime Manager.
Take-away: proof that a 612-line module can command $590 with good docs. Also one of two LGPL-3 modules, so its source is legally readable — useful as a reference implementation. Marketing page has an Odoo 18/19 version discrepancy; listing quality is uneven.

3 · ms_bitotime — Mohamed Saied

€69LGPL-35,249 LOCv17–19
The engineering sleeper: built-in job queue, idempotent pulls, schedule-aware interpretation.
  • Idempotent pulls: punches deduplicated by BioTime ID — re-running any synced period imports zero duplicates ("safely re-run anytime"). The most explicit duplicate-prevention guarantee on the market.
  • Built-in job queue (no OCA queue_job dependency): Jobs / Channels / Job Functions menus, job lifecycle states (Pending → Started → Done/Failed), UUID, retry counter, full error trace, one-click Requeue.
  • Channel serialization: a dedicated root.biotime channel runs one job at a time so parallel pulls never hammer the BioTime server; automatic retries after 1/5/10/30 minutes on server unavailability.
  • Interpretation quality: Late In / On Time status with exact late minutes from the real shift start; missing checkouts flagged for HR; night shifts kept as a single record spanning midnight.
  • Schedule is the baseline: changing an employee's working hours or grace period automatically re-evaluates already-imported punches.
  • Per-employee timezone so device clock mismatches don't create false "Late In" records; configurable re-pull overlap window and max shift length.
  • Pull Transactions (Advanced) wizard: date range, filter by device or single employee, optional direct-to-attendance transfer.
  • Dashboard: attendance chart, today's attendances, employees, total devices; quick-action pipeline Devices → Employees → Transactions → Attendance with live counters.
  • Raw transaction model with real device time, in/out state, source device and source server; "Is Transferred" flag.
Take-away: at €69 this is the best value and the deepest engineering on reliability + interpretation. It is the single most important benchmark for our build — and LGPL-3, so readable.

4 · de_zkbiotime_integration — Digital Economics LLC

$31–53OPL-11,350 LOCv18ZKBioTime 9.0
The most disciplined architecture per line of code: two-phase sync, per-punch error states, multi-company.
  • Two-phase sync: a fetch cron (default 30 min, configurable) is deliberately separated from a processing cron, so network failures never block attendance creation. The cleanest reliability idea on the market.
  • Per-punch lifecycle states: pending / processed / error / skipped, with the failure reason recorded, retry individually or in bulk, or skip with one click. Punches are stored pre-interpretation — a full audit trail.
  • Pairing engine with two modes: explicit (ZK punch_state 0 = check-in, 1 = check-out) and alternating (punches toggle in/out based on whether an open attendance exists).
  • Flexible employee matching: ZK Employee Code, Badge ID, or Identification Number; optional auto-creation of employees and departments from ZK data.
  • Device management: mirrors all terminals with online/offline status, user counts, fingerprint/face counts, firmware versions.
  • Configurable server timezone, punch times converted to UTC; multi-company with per-company server configs and record rules (multi-site support); verification types: fingerprint, face, card, palm, password.
  • Full Arabic (ar_001) localization — the only bilingual module.
  • Roadmap (i.e. gaps it admits): statistics dashboard, pushing employees Odoo → BioTime, webhooks, late/early alerts.
Take-away: the architectural reference for the staging/processing split and error recovery. Note it targets ZKBioTime 9.0 only, and its roadmap confirms nobody in this set does webhooks or two-way employee push well.

5 · biotime_server_integration — TKN Solutions

€120OPL-11,220 LOCv15–19
The two-way utility: download and upload employees, devices, shifts, period-based downloads.
  • Two-way employee sync: download employees from BioTime into Odoo and upload employees to BioTime (single or "upload all employees") — one of only two modules pushing data back.
  • Download devices; device records viewable in a Devices menu.
  • Download transactions by period (custom start/end date) plus automatic daily transaction downloads.
  • Shifts menu showing employee shifts assigned in BioTime.
  • Hourly cron auto-creating attendance from transactions; attendance linked and visible on transaction records.
  • Group-access integration controlling who sees the module; Test Connection as admin; "45 days free assistance" support model.
Take-away: widest version coverage (15–19) suggests a long-lived, simple codebase. Its differentiators are the upload direction and the shifts menu; its hourly-only cron is the loosest sync of the set.

6 · connector_biotime — Domiup

€80 + IAPOPL-12,904 LOCv16–19needs OCA queue_job
The broadest two-way connector: pushes departments, work locations and employees; pulls transactions; supports BioTime Cloud.
  • Push side (unique depth): Departments (hr.department), Work Locations (hr.work.location) and Employees, each with a "Push Now" button in a Push Actions tab — designed for initial master-data seeding at go-live. Employee push mode: All Employees vs Only Assigned.
  • Pull side: imports punch logs into biotime.transaction, only pulling transactions newer than a recorded Sync Last Date cursor; "Pull Now" for manual fetch.
  • BioTime Cloud support (since 18.0.1.0.4) — the only module connecting to ZKTeco's cloud API as well as on-prem.
  • Config: Host/IP, Port, Timezone, Punch State In / Punch State Out mapping, Is Cloud flag, Pull Transaction Mode (one request for all transactions vs one per device).
  • Transactions store Employee Code, Punch Time, State, Verify Type, Terminal Info; cron pairs valid IN/OUT punches into hr.attendance; linked attendance shown for traceability.
  • Background jobs via OCA queue_job (mandatory v19 prerequisite): retryable jobs, failed/incomplete transactions auto-retried up to a configurable limit.
  • Live demo server + YouTube walkthrough — strongest go-to-market packaging of the six.
Take-away: the reference for two-way scope and Cloud support. Cost of that breadth: a hard dependency on OCA queue_job, which is friction ms_bitotime explicitly avoids by shipping its own queue. €80 price is entry-level but in-app purchases are noted.

04What all six share — the table stakes

Every module, without exception, implements the same seven-part skeleton. This is the minimum viable product for this category, and any missing piece is an instant dealbreaker for buyers:

  1. Server configuration model — one record holding host/IP, port, username/password (token auth), plus sync settings; a Test Connection button validates credentials before anything runs.
  2. Employee mapping — a biotime_code-style field on hr.employee; punches link to Odoo employees through it. Weak mapping is the #1 support complaint in this category.
  3. Raw transaction staging — punches are stored first in their own model (source device, punch state, verify type, raw device time) before any interpretation, giving traceability and replay.
  4. Cron-driven pulling — scheduled actions fetch new transactions on an interval (7 min to daily across the set), with some form of incremental cursor so old data isn't re-fetched.
  5. Pairing engine — raw punches are converted into check-in/check-out pairs to create hr.attendance records, with duplicate prevention.
  6. Device/employee/transaction views — dedicated menus under the Attendances app so admins can inspect what was synced.
  7. Standard dependencies only — hr, hr_attendance, mail. Nothing else. (connector_biotime's extra OCA queue_job requirement is presented as friction by its competitor.)
Implication for us: table stakes are cheap to match — the differentiation budget should go to reliability (phase separation, queues, idempotency) and interpretation (late/missing/night-shift/timezone), because that is precisely where the six modules split into "thin cron script" and "real product".

05Differentiators, in three tiers

Tier A — decide before writing any code (architecture-level)

  • Two-phase sync (DE): fetch cron stores raw punches; a separate process cron interprets them. Network failures degrade fetching without ever blocking attendance creation.
  • Idempotency by BioTime transaction ID (MS): re-running any period imports zero duplicates — turns every operational mistake into a non-event.
  • Background job queue (MS built-in vs Do's OCA dependency): with retries (1/5/10/30 min backoff), serialized channels to protect the BioTime server, and a job UI with error traces and requeue. Shipping our own (MS-style) avoids the OCA dependency — a real selling point.
  • Per-punch lifecycle states pending → processed / error / skipped with recorded failure reasons and bulk retry/skip (DE): the difference between "sync silently drops data" and "HR can fix data".

Tier B — interpretation quality (what HR actually feels)

  • Late-in detection with exact minutes from the real shift start (MS, Hu, Ya) — using the employee's working schedule as the baseline.
  • Missing check-out flagging instead of silently wrong records (MS, Ya).
  • Night shifts as a single record spanning midnight (MS only — a genuine hole in every competitor).
  • Re-evaluation on schedule change (MS): editing working hours or grace periods re-computes already-imported punches.
  • Timezone correctness (MS per-employee; DE/Do server-level): device clock skew must not fabricate lateness.
  • Business-rule fields (Hu): break duration deduction, late tolerance, overtime threshold.

Tier C — scope & packaging

  • Two-way push (Do: departments, work locations, employees with Push Now; TK: employees): valuable at go-live for seeding BioTime from Odoo HR.
  • BioTime Cloud flag (Do only): cloud vs on-prem API endpoints.
  • Device monitoring (DE richest: online/offline, user/fingerprint/face counts, firmware) — turns the module into light access-control ops.
  • Dashboard + roles (Hu, MS) and multi-company (DE) — enterprise-readiness signals.
  • Advanced manual sync wizard (MS: date range × device × employee, optional direct transfer) — the tool support uses when a device was offline for a week.
  • Multiple auth schemes (Hu: Token/JWT/Basic) and pull granularity (Do: one request for all vs per device).

06Gaps nobody covers — our opening

  • Real-time ingestion. Every module polls on cron. DE lists webhooks on its roadmap — meaning even its author considers it unsolved. BioTime supports transaction webhooks/HTTP listeners; a webhook endpoint plus the staging table would give us true real-time attendance with cron as fallback.
  • Reliability + interpretation together. DE owns error recovery but has no late/night-shift logic; MS owns interpretation but its error states are job-level, not punch-level. No module combines both.
  • Cloud and on-prem in one product. Only Do supports Cloud, and it lacks interpretation quality. A connector that auto-detects cloud vs on-prem endpoints would be first.
  • Multi-company + per-employee timezone together — DE and MS each hold one half.
  • Overtime/leave integration. Only Hunter touches overtime, and only as a threshold rule. Linking punches to Odoo overtime requests, extra hours and payslips is untouched territory.
  • Alerting. Late arrival / early departure / device-offline notifications (DE roadmap again) — missing across the board.

07Recommended blueprint for our module

Model layout

biotime.server          host, port, auth mode (token/JWT/basic), credentials,
                        timezone, page size, pairing mode, punch_state_in/out,
                        sync interval, last_sync_date, is_cloud, active, company_id
biotime.transaction     (staging) biotime_id [unique], employee_code, punch_time_utc,
                        punch_state, verify_mode, terminal_sn, terminal_name,
                        state: pending | processed | error | skipped,
                        error_msg, attendance_id, server_id
biotime.device          sn, name, ip, state, user/fp/face counts, firmware, last_activity
biotime.job             (built-in queue) server, method, state, retries, next_retry,
                        error_trace, channel  ← serialized per server
hr.employee (inherit)   biotime_code, biotime_server_id

Sync flow

  1. Fetch cron / webhook — pull new transactions (incremental cursor per server; overlap window for clock skew) and store them raw, keyed by BioTime transaction ID. Nothing is interpreted here.
  2. Process cron — map employee (code → badge → ID fallback, like DE), pair punches (explicit mode default, alternating fallback), create hr.attendance, mark transactions processed or error with a reason.
  3. Queue layer — every remote call runs as a job with exponential retry; one job at a time per server so BioTime is never hammered.
  4. HR layer — late-in minutes, missing-checkout flags, night-shift merging, per-employee timezone, re-evaluation when the working schedule changes.
  5. Surfaces — sync log + job board, device monitor, dashboard, manual wizard (period × device × employee).
Phasing suggestion: MVP = table stakes + Tier A reliability (idempotency, two-phase, simple queue) — that alone matches the best product in the market. Phase 2 = Tier B interpretation. Phase 3 = two-way push, Cloud, dashboard, alerts, webhooks.

08Risks & notes for the build

  • License discipline. Four of six modules are OPL-1 proprietary — feature inspiration is fine, code is not. ms_bitotime and yasir are LGPL-3 and legally readable: use them as reference implementations, never copy assets or text.
  • BioTime API versioning is the top technical risk. DE supports only ZKBioTime 9.0 (REST); Yasir targets 8.5; Do needed a separate Cloud flag. Before any code, pin down the client's exact BioTime version(s) and verify endpoints and the punch_state codes against it (0 = check-in, 1 = check-out is confirmed by the listings; other states need verification).
  • Listing claims ≠ behavior. This research is from vendor pages; several claims (e.g. yasir's Odoo 18/19 inconsistency, Hunter's conflicting prices €449/€649) show listings can be sloppy. Buying ms_bitotime (€69) and DE ($31) as reference products would be cheap due diligence.
  • The queue decision. OCA queue_job is mature but adds a dependency buyers must install; ms_bitotime proves a compact built-in queue is viable and marketable ("no external dependencies"). Recommend built-in, channel-serialized.
  • Interval expectations. Cron intervals in the wild range 7 min to hourly. With webhooks in Phase 3 we can beat the entire market on freshness; until then, default to 10–15 min and make it configurable.
